# 方案二动机实验结果分析报告

## 1. 结论摘要

本组实验形成了较完整的证据链：图索引为更新预留了固定容量，但查询真正需要的邻接表长度随节点变化；每次读取完整记录会浪费接近一半的 RDMA 传输，而“先读长度、再读内容”又会引入第二次依赖 RDMA。方案二利用查询前已知的有效长度，一次性只读取有效前缀，从而同时避免无效字节和额外往返。

主要结果如下：

- 在 394,405,526 次实际扩展节点采样中，节点平均有效邻居数为 **47.09**，平均只需读取 **419.51 B**；固定读取 **832 B** 时，平均浪费 **412.49 B（49.58%）**。
- 在 160 个活跃 QP 的远程读取微基准中，一次按需读取达到 **26.62 M logical reads/s**，分别比固定完整读取和两阶段依赖读取高 **89.10%**、**148.81%**。
- 在 SIFT100M 端到端查询中，方案二将图数据传输量降低 **49.58%**，RDMA 等待时间降低 **25.81%**，查询吞吐从 **58.79 KQPS** 提升到 **67.30 KQPS（+14.48%）**，P99 延迟从 **6.196 ms** 降到 **5.305 ms（-14.38%）**。
- 两种模式的 Recall@10 均为 **0.9401**，按需读取期间没有发生 full-read 或 fallback，说明本次性能收益没有以查询精度或错误恢复为代价。

因此，现有数据足以支撑方案二的核心动机和有效性：**固定容量适合容纳动态更新，但不应直接成为查询的传输粒度；将有效长度暴露给查询路径，可以把“固定布局”和“按需传输”解耦。**

## 2. 实验回答的问题

| 实验 | 要回答的问题 | 观测指标 |
|---|---|---|
| 有效邻接长度分布 | 完整读取究竟浪费多少数据？ | 平均度数、所需字节、浪费比例、P50/P95 |
| 三种 RDMA 读取方式 | 为什么不能使用完整读取或先读 header？ | logical reads/s、批次 P50/P99 延迟 |
| 端到端对照 | 方案二能否转化为系统收益？ | QPS、查询延迟、传输字节、RDMA 等待、Recall |

端到端实验使用 SIFT100M、256 个客户端线程、10 秒预热和 30 秒测量；Fixed 与 LiveExtent 使用相同的查询系统配置，仅图邻接记录的读取策略不同。微基准每批包含 16 个逻辑记录访问，在 1、32、160 个活跃 QP 下各重复 3 次，报告中使用中位数。

## 3. 动机一：固定完整读取浪费近一半带宽

### 3.1 有效长度分布

固定邻接记录大小为 832 B。对 LiveExtent 运行中实际被查询扩展的 394,405,526 个节点进行统计，结果如下：

| 指标 | 结果 |
|---|---:|
| 平均有效邻居数 | 47.09 |
| 平均所需前缀 | 419.51 B |
| 固定完整读取 | 832 B |
| 平均无效传输 | 412.49 B |
| 平均浪费比例 | 49.58% |
| 所需前缀 P50 | 400 B |
| 所需前缀 P95 | 784 B |

平均节点只使用了约一半的预留空间。若查询无条件读取 832 B，则每访问一个图节点平均有 412.49 B 不参与计算，却仍然消耗 PCIe/RDMA 链路和内存系统带宽。这不是少量对齐开销，而是可被直接优化掉的大块数据。

### 3.2 分布并不允许使用一个全局短长度

节点度数并非集中在一个固定值。主要区间的访问占比如下：

| 有效邻居数区间 | 访问占比 |
|---|---:|
| 0–24 | 12.31% |
| 25–40 | 32.66% |
| 41–56 | 26.65% |
| 57–72 | 14.41% |
| 73–88 | 7.56% |
| 89–96 | 6.42% |

P50 所需长度为 400 B，但 P95 已达到 784 B。这说明把所有读取统一缩短到 400 B 会截断大量长邻接表，无法保证正确性。真正需要的是**每个节点独立的有效长度**：短记录少读，长记录仍完整读取。

这组分布同时解释了方案二为什么不是简单地调小记录大小。固定的 832 B 是动态更新所需的容量上限；查询需要的是该记录当前的有效前缀，两者具有不同语义。

## 4. 动机二：先读 header 再读邻居会增加依赖往返

微基准比较了三种协议：

1. **Fixed-full**：一次读取完整的 832 B 记录。
2. **Header+body**：先读取 16 B header，完成后再发起 384 B body 读取，总有效载荷为 400 B，但存在两阶段依赖。
3. **Hinted one-read**：查询侧预先知道有效长度，一次读取 400 B 有效前缀。

其中 400 B 对应分布的中位所需长度，目的是隔离协议本身的代价；它不是用一个固定 400 B 替代实际的逐节点长度。

### 4.1 吞吐结果

| 活跃 QP | Fixed-full | Header+body | Hinted one-read | Hinted 相对 Fixed | Hinted 相对 Header+body |
|---:|---:|---:|---:|---:|---:|
| 1 | 1.308 M/s | 0.692 M/s | 1.350 M/s | +3.21% | +95.12% |
| 32 | 14.053 M/s | 17.659 M/s | 27.944 M/s | +98.85% | +58.25% |
| 160 | 14.076 M/s | 10.698 M/s | 26.618 M/s | +89.10% | +148.81% |

这里的 logical read 表示完成一次邻接记录访问；Header+body 的两条物理 RDMA Read WQE 合并计为一个 logical read。因此，表中的比较没有把两阶段协议的 WQE 数误当成应用访问数。

### 4.2 尾延迟结果

下表是每批 16 次逻辑读取的 P99 完成时间，不是单次读取延迟：

| 活跃 QP | Fixed-full | Header+body | Hinted one-read |
|---:|---:|---:|---:|
| 1 | 14.336 μs | 25.600 μs | 13.312 μs |
| 32 | 43.008 μs | 31.744 μs | 20.480 μs |
| 160 | 185.344 μs | 306.176 μs | 123.904 μs |

结果应作如下理解：

- 低并发下，完整读取和按需一次读取都只经历一次 RDMA，链路尚未被带宽压满，因此两者吞吐接近；两阶段协议因额外依赖往返而明显较慢。
- 32 QP 时，Header+body 因减少传输字节而暂时超过 832 B 完整读取，但仍远低于一次按需读取。减少字节是有价值的，但没有必要为此付出第二个依赖阶段。
- 160 QP 时，完整读取受大载荷限制，两阶段读取又受到额外 WQE、CQE 和串行依赖限制；一次按需读取同时避开两类开销，吞吐最高且 P99 最低。

因此，实验不是要声称 Header+body 在每一个并发点都比完整读取差，而是说明两种朴素方案各有一个根本缺陷：**完整读取浪费带宽，Header+body 增加协议工作量和依赖链；一次按有效长度读取才同时满足“小载荷”和“单阶段”。**

## 5. 端到端有效性：节省的字节转化为查询性能

| 指标 | Fixed 832 B | LiveExtent | 变化 |
|---|---:|---:|---:|
| 查询吞吐 | 58,785 QPS | 67,300 QPS | **+14.48%** |
| 平均延迟 | 4.353 ms | 3.802 ms | **-12.66%** |
| P50 延迟 | 4.278 ms | 3.750 ms | **-12.34%** |
| P95 延迟 | 5.551 ms | 4.783 ms | **-13.84%** |
| P99 延迟 | 6.196 ms | 5.305 ms | **-14.38%** |
| P999 延迟 | 7.081 ms | 5.994 ms | **-15.34%** |
| 图数据字节/查询 | 162,626 B | 81,994 B | **-49.58%** |
| 图 RDMA WQE/查询 | 195.464 | 195.420 | -0.02% |
| GPU RDMA 等待/查询 | 1,477.69 μs | 1,096.26 μs | **-25.81%** |
| GPU 查询时间 | 4,275.38 μs | 3,711.45 μs | **-13.19%** |
| Recall@10 | 0.9401 | 0.9401 | 不变 |

最关键的因果证据是：图数据字节/查询减少了 49.58%，但物理图读取 WQE/查询仅变化 -0.02%。也就是说，两种模式访问了几乎相同数量的图节点，方案二并没有通过少搜索节点来“换取”吞吐，而是让每次访问只搬运有用字节。

字节下降进一步带来每查询 RDMA 等待时间下降 381.43 μs（25.81%），最终体现为 QPS 提高 14.48% 和 P99 降低 14.38%。端到端收益小于微基准中的峰值收益是正常的：完整查询还包含候选管理、PQ 距离计算、beam 合并和精确重排等工作，方案二只优化其中的图记录传输部分。

## 6. 正确性与运行状态

- Fixed 和 LiveExtent 的 Recall@10 都是 0.9401，说明读取有效前缀没有改变搜索结果质量。
- LiveExtent 共执行 394,640,811 次图记录读取，其中 live-extent read ratio 为 1.0，full record read 为 0。
- dynamic fallback read 为 0，说明本次静态快照中长度元数据与图记录一致，结果没有混入 fallback 完整读取。

这能够证明静态 SIFT100M 查询公共路径上的 LiveExtent 正确性。不过，fallback 为 0 不等于已经验证了更新并发下的陈旧提示修复；那属于单独的动态压力实验。

## 7. 可用于论文的证据链

可以将本组结果压缩为如下叙事：

> 动态图记录需要按最大度数预留固定空间，但实际查询访问的节点平均只有 47.09 个有效邻居，使固定 832 B RDMA Read 中有 49.58% 的字节无效。先读取长度再读取邻居虽能减少数据，却增加一轮依赖 RDMA；在 160 QP 下，其吞吐比一次按需读取低 59.81%。通过在发起请求前获得有效长度，LiveExtent 以一次 RDMA 只读取有效前缀，使端到端图流量下降 49.58%、RDMA 等待下降 25.81%，最终将查询吞吐提高 14.48%，同时保持 Recall@10 不变。

建议论文使用两张图：

- `program2_motivation.svg`：左侧展示有效邻接长度分布/完整读取浪费，右侧展示三种 RDMA 方式。它回答“为什么需要方案二”。
- `program2_effectiveness.svg`：展示端到端 QPS、P99、图传输字节和 Recall。它回答“方案二是否有效”。

如果版面只能保留一张图，建议把“平均有效字节与固定 832 B 的对比”和“端到端 QPS 提升 14.48%”组合成一张双子图，分别覆盖动机和最终收益。

## 8. 当前实验的边界与补强建议

现有数据已经适合作为内部分析和论文初稿，但正式论文出图前建议注意以下边界：

1. **端到端 Fixed/LiveExtent 当前各运行一次。** 建议最终各重复至少 3 次并交错顺序，报告均值、标准差或 95% 置信区间，以排除机器状态和执行顺序造成的波动。
2. **两种模式按相同 30 秒时长测量。** LiveExtent 因吞吐更高而处理了更多请求；这适合比较稳态吞吐。若要进一步强化延迟结论，可补充相同查询条数、相同查询序列的配对实验。
3. **分布是查询加权分布。** 394,405,526 个样本来自实际被扩展节点，正好反映查询路径的带宽浪费，但不能直接解释为“全图所有节点”的静态度分布。
4. **微基准的 400 B 是代表性长度。** 它用于比较协议代价；实际系统按每个节点的有效长度读取，端到端 49.58% 的字节下降才是对真实长度分布的加权结果。
5. **当前运行验证的是静态公共路径。** 若论文还要强调 DynaExtent 在更新、槽位复用或元数据暂时不一致时的能力，应另测混合读写、热点更新及 fallback/self-healing 行为。

这些限制不会推翻当前结论，但应避免把本次结果扩大表述为尚未测量的动态一致性结论。
