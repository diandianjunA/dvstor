# 方案二动态场景动机与有效性实验分析报告

## 1. 结论概览

本次实验在持续执行 `500 update/s` 的动态场景下，对比了三种真实可实现的远程邻接读取方式：

1. **Fixed**：每次读取完整的 832 B 图记录；
2. **Header→Neighbor**：先读取 16 B Header，再根据其中的长度读取 Neighbor；
3. **ClassExtent**：使用长度类别预测本次需要读取的范围，通常只进行一次 RDMA，低估时再 fallback。

实验得到三个清晰结论：

- 查询实际访问的动态节点平均只有 **41.50 个邻居**，理想情况下只需读取 **347.99 B**。Fixed 每次读取 832 B，其中平均 **58.2% 的字节没有被使用**。
- Header→Neighbor 的传输量几乎等于 Oracle，但需要约 **2 次串行 RDMA/邻接访问**。它的查询吞吐只有 **50.67 KQPS**，甚至比 Fixed 低 **14.3%**，说明仅仅减少字节并不足以解决问题。
- ClassExtent 的实际动态读取量为 **377.29 B/节点**，只比不可实现的 Oracle 下界高 **8.42%**，同时基本保持一次 RDMA。它达到 **66.83 KQPS**，相比 Fixed 提升 **13.0%**，相比 Header→Neighbor 提升 **31.9%**。

ClassExtent 在 393 万次动态节点展开中只发生 **11 次 fallback**，比例约为 **0.00028%**，约每 **35.8 万次**短读才发生一次。这说明长度 class 的粒度和自适应更新机制是合理的。

## 2. 实验设置与有效性检查

三个 case 均采用相同配置：

| 项目 | 配置 |
|---|---:|
| 数据集 | SIFT100M |
| 预热时间 | 5 s |
| 正式测量时间 | 20 s |
| 更新目标速率 | 500 update/s |
| 专用更新线程 | 16 |
| 查询负载 | 256 个查询线程闭环饱和 |
| 更新类型 | Insert |
| 每个 case 完成更新 | 10,000 |

负载公平性如下：

| 策略 | 更新吞吐 | 更新完成数 | 更新达成率 | 最低 5 s 窗口更新吞吐 |
|---|---:|---:|---:|---:|
| Fixed | 500.0/s | 10,000 | 100% | 499.8/s |
| Header→Neighbor | 500.0/s | 10,000 | 100% | 499.8/s |
| ClassExtent | 500.0/s | 10,000 | 100% | 499.8/s |

因此，三个策略是在相同更新压力下进行比较的，不存在某个策略因为少处理更新而获得更高查询吞吐的问题。三个 case 均没有 direct-path failure，也没有查询或更新零完成窗口。

## 3. 动机：动态邻接长度造成了什么问题

### 3.1 查询真正需要读取多少数据

ClassExtent case 共记录了 **3,931,431 次权威动态节点展开**。这里的分布是“查询访问加权”的：一个动态节点被查询访问多次，就会被统计多次，因此它比对所有节点做静态扫描更能反映实际 RDMA 流量。

| 指标 | 结果 |
|---|---:|
| 平均动态邻居数 | 41.50 |
| P50 邻居数上界 | 40 |
| P95 邻居数上界 | 88 |
| Oracle 平均读取长度 | 347.99 B |
| Class 向上取整后的理论长度 | 375.67 B |
| Fixed 读取长度 | 832 B |

Oracle 按下面的方式离线计算：

```text
Oracle bytes = 16 B Header + 实际邻居数 × 8 B
```

Oracle 使用的是节点完成读取、版本校验并正式展开后的真实邻居数。它假设查询在发起 RDMA 前能够零开销知道这个长度，因此只是理论下界，并不是一种可部署策略。

### 3.2 Fixed 为什么浪费

平均每次动态邻接访问真正需要 347.99 B，而 Fixed 固定读取 832 B：

```text
无效字节 = 832 - 347.99 = 484.01 B
无效字节占 Fixed 传输的比例 = 484.01 / 832 = 58.2%
```

也可以从另一个角度表述：Fixed 的传输量是 Oracle 的 **2.39 倍**，比 Oracle 多传输了 **139.1%**。

这给出了方案二最直接的动机：图节点的有效邻接长度远小于物理记录容量，完整读取会持续浪费 RDMA 带宽。

### 3.3 Header→Neighbor 为什么仍然不好

Header→Neighbor 先读取 16 B Header，再读取精确长度的 Neighbor body。从字节数看，它几乎达到 Oracle：

| 方法 | 动态读取字节/展开节点 | 物理 RDMA/展开节点 |
|---|---:|---:|
| Fixed | 833.89 B | 1.0023 |
| Header→Neighbor | 347.85 B | 2.0023 |
| Oracle | 347.99 B | 1.0000 |

但第二次 RDMA 必须等待第一次 Header RDMA 返回后才能构造，形成了串行依赖。实验中每个查询的物理图读取数从 Fixed 的 **191.56** 增加到 Header→Neighbor 的 **383.02**，基本翻倍。

结果是，Header→Neighbor 虽然将每查询图读取字节降低 **52.9%**，查询吞吐却从 59.14 KQPS 降到 50.67 KQPS，下降 **14.3%**；GPU RDMA 等待时间从 1442.0 μs/query 增加到 2061.7 μs/query，增加 **43.0%**。

因此，两种传统做法分别受制于不同问题：

- Fixed：一次读取，但传输大量无效字节；
- Header→Neighbor：字节精确，但引入两次串行 RDMA。

这正是方案二需要同时解决的两个矛盾。

## 4. 方案有效性：ClassExtent 的端到端收益

### 4.1 查询吞吐和延迟

| 策略 | 查询吞吐 | 平均延迟 | P99 延迟 | RDMA 等待/query |
|---|---:|---:|---:|---:|
| Fixed | 59.14 KQPS | 4.327 ms | 6.284 ms | 1442.0 μs |
| Header→Neighbor | 50.67 KQPS | 5.051 ms | 6.979 ms | 2061.7 μs |
| ClassExtent | **66.83 KQPS** | **3.830 ms** | **5.413 ms** | **1122.5 μs** |

ClassExtent 相比 Fixed：

- 查询吞吐提升 **13.0%**；
- 平均延迟降低 **11.5%**；
- P99 延迟降低 **13.9%**；
- GPU RDMA 等待时间降低 **22.2%**；
- 每查询图读取字节从 159.38 KB 降至 80.34 KB，降低 **49.6%**。

ClassExtent 相比 Header→Neighbor：

- 查询吞吐提升 **31.9%**；
- P99 延迟降低 **22.4%**；
- GPU RDMA 等待时间降低 **45.6%**。

Header→Neighbor 每查询传输的字节数比 ClassExtent 少约 7.0%，但性能反而明显更差。这进一步说明，在小粒度图访问中，避免串行 RDMA 往返比追求绝对最少的几个字节更加重要。

### 4.2 ClassExtent 距离 Oracle 有多远

| 指标 | Oracle | Class 理论值 | ClassExtent 实测值 |
|---|---:|---:|---:|
| 动态字节/展开节点 | 347.99 B | 375.67 B | 377.29 B |
| 相比 Oracle 额外字节 | 0% | 7.96% | 8.42% |
| RDMA/展开节点 | 1.0000 | 1.0000 | 1.0023 |

Class 的 8 邻居粒度只带来平均 **27.69 B** 的向上取整开销。实际读取量仅比理论 class 长度多 **0.43%**，说明重试和 fallback 并没有显著放大流量。

与 Fixed 的实际动态流量相比，ClassExtent 将每个权威动态展开对应的物理读取量降低 **54.8%**。它没有达到 Oracle 的绝对最小字节数，但以约 8.4% 的字节冗余换取了近似一次 RDMA 的读取路径，是一个很好的带宽与往返次数折中。

### 4.3 Fallback 是否会抵消收益

ClassExtent 的动态遥测如下：

| 指标 | 数值 |
|---|---:|
| 动态短读 | 3,933,329 |
| 动态全长读 | 7,076 |
| underhint fallback | 11 |
| fallback 比例 | 0.000280% |
| hint promotion | 9 |
| hint demotion | 0 |

Fallback 比例约为 **1 / 357,575**。即使考虑普通快照重试，ClassExtent 的物理 RDMA 数也只有 1.0023 次/权威动态展开，与 Fixed 的 1.0023 次几乎相同，远低于 Header→Neighbor 的 2.0023 次。

这说明：

1. 当前 class 粒度已经能够覆盖绝大多数动态长度变化；
2. 旧 hint 导致的低估非常少；
3. promotion 能够修复观察到的低估；
4. fallback 只是保证正确性的罕见慢路径，不会抵消一次读取带来的收益。

## 5. 查询质量和运行稳定性

三个 case 的 Recall@10 都为 **0.9401**，结果集均完整。需要注意，该 Recall 检查发生在正式 mixed 性能阶段之前，因此它适合作为“三个 case 初始查询配置一致”的控制项，不能单独作为动态更新后质量不变的证据。

20 秒正式测量被划分为四个 5 秒窗口。三个策略的查询尾部/头部吞吐比分别为：

| 策略 | 尾部/头部查询吞吐比 | 最低窗口查询吞吐 |
|---|---:|---:|
| Fixed | 1.0026 | 58.89 KQPS |
| Header→Neighbor | 1.0018 | 50.45 KQPS |
| ClassExtent | 1.0020 | 66.64 KQPS |

三个 case 都没有随时间衰减，更新吞吐在每个窗口中也稳定在约 500/s，因此性能差异不是由运行抖动或更新积压造成的。

## 7. 证据边界与后续建议

本次实验中，动态版本占所有权威展开节点的比例约为 **1.53%**，且当前 graph-read policy 同时作用于静态节点和动态节点。因此，应准确区分本实验能够支持的结论：

**可以直接支持：**

- 在真实持续更新负载下，ClassExtent 完整系统比 Fixed 和 Header→Neighbor 更快；
- 对实际访问的动态版本，ClassExtent 的读取字节数非常接近 Oracle；
- 动态 hint 的 fallback 极少，class 设计有效；
- 收益不是通过降低更新吞吐或牺牲当前控制项中的 Recall 得到的。

**不能仅由本实验单独声称：**

- 13.0% 的全部端到端吞吐提升都来自动态节点。因为静态节点也使用了对应策略，而动态节点只占约 1.53% 的权威展开。

如果需要完全排除“静态节点长度可以预先缓存在计算节点”的审稿意见，最严格的补充对照应让三个策略对静态节点统一使用本地已知长度，只在动态节点上分别采用 Fixed、Header→Neighbor 和 ClassExtent。当前结果已经能够完整支撑方案的系统有效性、Oracle 接近程度和 fallback 合理性，但上述补充实验会进一步隔离方案针对动态长度的净收益。
