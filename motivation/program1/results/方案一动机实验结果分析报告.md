# 方案一动机实验结果分析报告

> **2026-08-22 校正说明：** 后续代码审查发现，本次报告中的 25.13% 只是旧版保守子计数，并未覆盖完整的跨分片 global continuation；其中部分 `*_read_ns` 还包含本地快照访问。因此它不能作为最终“纯 RDMA 占比”。实验代码现已增加本地 Stage1、全局 continuation、最终候选读取和远程反向更新的互斥计时，需用修复后的版本重跑 baseline 后再绘制最终堆叠柱。本报告其余数字仍用于记录旧轮次。

## 1. 实验概况

- 结果目录：`program1_20260822_215459`
- 数据集与索引：SIFT100M，schema 16，两个 case 使用相同 index prefix 和 build fingerprint
- 对照组：`coupled`，更新完成前执行完整同步更新
- 方案组：`decoupled`，Stage1 完成后返回，Stage2 后台执行
- 负载：insert-only，16 个客户端线程
- 每组：预热 128 次插入，正式测量 1000 次插入
- 精度实验：插入 1000 个新向量，抽样查询其中 100 个，统计 self-hit\@10
- 重复次数：1

两个性能 case 除更新完成模式外，索引、插入 ID 起点、线程数和 GPU/RDMA 模式均一致。细粒度 breakdown 已成功启用，基线的控制页 RDMA 计数非零，因此实验 1、2 的原始数据有效。

## 2. 核心结论

1. **同步完整更新中，远程 RDMA 依赖约占关键路径的 25.13%。** 平均每次插入的远程依赖时间为 11.05 ms，其中远程读取为 3.47 ms，远程反向边更新为 7.59 ms。这说明将跨分片依赖移出前台 ACK 路径具有明确动机，但不能声称 RDMA 是全部开销或唯一瓶颈。
2. **方案一显著提高了前台更新性能。** 插入吞吐从 353.98 ops/s 提高到 2264.86 ops/s，即 **6.40×**；平均 ACK 延迟从 44.58 ms 降至 6.96 ms，下降 **84.38%**；P99 从 242.10 ms 降至 18.41 ms，下降 **92.40%**。
3. **Stage1-only 已能检索大部分新节点，但当前结果不支持“精度损失很小”的强结论。** Stage1-only self-hit\@10 为 80%，Stage2 完成后为 100%，相差 20 个百分点。它证明 Stage1 提供了立即可见性，但这次样本下的短期质量差距仍然明显。
4. **Stage2 最终能够排空。** 方案组在 1000 次前台插入结束后，用 95.97 ms 将 durable watermark 追到 target watermark，5 个分片均相等，且失败数为 0。但本次遥测快照没有采到单节点 Stage2 完成延迟样本，因此不能计算“每个节点平均多久完成 Stage2”。
5. **本次不能判断迁移是否改善跨分片边比例。** locality 计数全为 0 是遥测窗口未覆盖 Stage2 工作导致的缺失值，不代表跨分片边比例为 0，也不代表迁移没有作用。

## 3. 实验 1：同步更新中的 RDMA 开销

| 组成               |      每次插入平均时间 |  占同步关键路径比例 |
| ---------------- | ------------: | ---------: |
| 远程图/向量读取等待       |      3.467 ms |      7.88% |
| 远程反向边更新          |      7.587 ms |     17.25% |
| **远程 RDMA 依赖合计** | **11.055 ms** | **25.13%** |
| 其余本地计算与协议工作      |     32.938 ms |     74.87% |
| **同步更新关键路径合计**   | **43.993 ms** |   **100%** |

客户端观测到的平均延迟为 44.577 ms，与存储端累计的 43.993 ms 基本吻合，说明控制页 breakdown 能合理解释同步更新路径。

可以用于论文的表述：

> 即使更新已经卸载到存储节点，完整同步更新仍需在 ACK 前等待跨分片读取和远程反向边维护；这些远程依赖占同步关键路径的 25.1%，平均增加约 11.1 ms。因此，我们将其从可见性关键路径移至异步 Stage2。

不建议写成“RDMA 主导全部更新开销”，因为本次测得的占比是约四分之一，而不是超过一半。

## 4. 实验 2：开启方案一后的更新性能

| 指标                          | Coupled baseline |     Two-stage |            改善 |
| --------------------------- | ---------------: | ------------: | ------------: |
| 前台插入吞吐                      |     353.98 ops/s | 2264.86 ops/s |     **6.40×** |
| 含 Stage2 drain 的 durable 吞吐 |     353.97 ops/s | 1860.48 ops/s |     **5.26×** |
| 平均 ACK 延迟                   |         44.58 ms |       6.96 ms | **下降 84.38%** |
| P50 ACK 延迟                  |         24.02 ms |       5.86 ms |     下降 75.62% |
| P95 ACK 延迟                  |        165.09 ms |      15.33 ms |     下降 90.72% |
| P99 ACK 延迟                  |        242.10 ms |      18.41 ms | **下降 92.40%** |
| P99.9 ACK 延迟                |        316.56 ms |      22.15 ms |     下降 93.00% |

前台吞吐和 durable 吞吐应分开报告：6.40× 表示用户可见的 Stage1 完成速率；5.26× 将测量结束后的 Stage2 排空时间也计算在内。两种口径都明显优于 coupled baseline。

性能提升不能全部归因于“移走了 25.13% 的 RDMA 时间”。Two-stage 同时缩短了搜索、剪枝和全局维护范围，所以 6.40× 是整个两阶段边界设计的综合收益。

## 5. 实验 3：Stage1-only 的短期查询质量

| 阶段          | self-hit\@10 | 命中数/查询数 |
| ----------- | -----------: | ------: |
| Stage1-only |          80% |  80/100 |
| Stage2 完成后  |         100% | 100/100 |
| 差值          |      20 个百分点 |  20 个查询 |

有效性检查通过：

- Stage2 人工延迟：15 s
- 插入加 Stage1-only 查询耗时：0.496 s
- `stage1_only_window.valid = true`

因此第一次查询确实发生在 Stage2 开始前，80% 是有效的 Stage1-only 结果。作为抽样不确定性参考，80/100 的 Wilson 95% 区间约为 71.1%–86.7%；100/100 的区间约为 96.3%–100%。

需要注意：这里测量的是“用新插入向量作为查询时，其自身 ID 是否出现在 Top-10”，即 self-hit\@10，不是标准 SIFT Recall\@10。它适合证明新节点的即时可检索性，但不能替代包含动态 ID 的完整 ground truth recall。

基于当前结果，安全的论文表述是：

> Stage1 在完整全局维护前已使 80% 的抽样新节点能够被 Top-10 查询命中，Stage2 完成后恢复到 100%。

当前不建议表述为“Stage1 几乎不损失精度”，因为 20 个百分点的差距不算小。若希望支持这一论断，需要增大查询样本、调整 Stage1 构图质量，或者使用标准动态 ground truth 重新测量。

## 6. 实验 4：Stage1 到 Stage2 的完成时间

本次可以确认：

- 1000 次更新完成前台 ACK 后，剩余 Stage2 debt 在 95.97 ms 内排空；
- 5 个分片的 `maintenance_durable_sequences` 与 `maintenance_target_sequences` 完全相等；
- `maintenance_drain complete=yes`；
- Stage2 terminal failure 为 0。

但报告中的以下字段没有样本：

```text
stage2_finalized_live_delta = 0
p99_stage2_delay_samples = 0
avg_stage2_delay_ms = 0
```

这里的 0 是因为固定 1000 次操作只运行了 0.442 s，Stage2 控制页累计快照没有在有效 Stage2 工作之后再次发布；并非 Stage2 延迟真的为 0。因此，95.97 ms 只能解释为“测量结束后的整体 backlog drain 时间”，不能除以 1000 当作每个节点的平均 Stage2 延迟。

结论状态：**最终排空有效；单节点平均/P99 Stage2 延迟缺失，需要补测。**

## 7. 实验 5：迁移对物理局部性的影响

本次报告中：

```text
stage2_final_edges = 0
stage2_cross_edges_stage1_home = 0
stage2_cross_edges_final_home = 0
stage2_migrations = 0
```

这些字段与 `stage2_finalized_live_delta = 0` 同时出现，说明 begin/end 快照没有覆盖 Stage2 finalization，而不是索引真的不存在跨分片边。三个 0 无法形成比例，`cross_edge_reduction_ratio = 0` 也没有统计意义。

结论状态：**本次不能验证迁移思路，需要补测 Stage2/locality 遥测。**

## 9. 最终评价与建议

当前结果已经能够形成一条清晰的前半段动机链：

```text
同步更新约 25% 的关键路径花在远程依赖
        ↓
将全局工作移到 Stage2
        ↓
前台吞吐提高 6.40×，P99 降低 92.40%
        ↓
Stage1 能立即检索 80% 的抽样新节点，Stage2 后恢复到 100%
```

但后半段“精度损失持续时间很短”和“迁移改善物理局部性”还没有被当前快照数据证明。建议只补跑 solution case，并让测量持续超过一次遥测发布周期，或者在 drain 后显式刷新一次控制页遥测；不需要重新跑已有效的 coupled breakdown 和 Stage1-only 实验。

正式论文中还应将 baseline/solution 至少重复 3 次，并报告均值和误差条。当前单次结果的提升幅度很大，适合确认动机和调试实验设计，但还不足以单独作为最终统计结果。
